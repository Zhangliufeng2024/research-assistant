# 科研操作系统重构计划（2026-08-24）

> 目标：借鉴 Codex app 的“统一 Agent 工作空间”交互模式，同时保留并强化本项目的科研优势，
> 将研究助手重构为：**以研究项目为中心，以 Agent 任务为执行单元，以证据链为知识骨架，
> 以产物审阅为交互核心的科研操作系统**。

## 0. 设计基线与不变原则

### 0.1 借鉴的产品原则

Codex app 的可借鉴内核不是某个页面样式，而是统一的工作循环：

```text
项目 / 工作区
  → 线程（Thread）
  → 回合（Turn）
  → 结构化事件与 Agent 项目（Item）
  → 文件/工具/测试结果
  → 变更审阅
  → 继续、分支、归档或调度
```

官方 Codex app-server 将 Thread、Turn、Item、流式通知、thread resume/fork、turn steer
作为核心交互原语；官方桌面产品则把项目、文件、长任务、并行工作和可审阅产物放在同一
工作空间中。研究助手将采用同样的交互骨架，但把 Item 和审阅对象扩展为科研证据、主张、
实验运行和论文产物。参考：OpenAI Codex App Server、ChatGPT desktop app、Codex long-horizon
tasks 文档。

### 0.2 必须保留并继续强化的科研能力

- Citation Gate：真实 DOI / 标题 / BibTeX 核验。
- Doc Gate：文档生成、结构、字数、格式和产物完整性检查。
- ArtifactStore：阶段级检查点、hash 校验、精确续跑。
- 论文专用多 Agent pipeline：规划、文献/图表、组装、审阅。
- 资料库：PDF / DOCX / Markdown / TXT / BibTeX，带页码/片段/hash 锚点。
- 文件变更版本化、diff、恢复和工作区安全围栏。
- SQLite WAL durable task、事件回放、任务 DAG、运行指标。

### 0.3 非目标

- 本阶段不处理跨平台重构。
- 不直接复制 Codex 的代码专用 UX；科研对象和科研质量门禁优先。
- 不引入必须联网的基础能力；离线资料库和确定性检索继续可用。
- 不破坏既有 API、任务目录、`run.json`、`events.jsonl`、`.ra` 数据库迁移能力。

## 1. 目标架构

```text
ResearchOSKernel
├── ProjectSpace                # 项目、工作区、成员/权限、项目指令
├── ThreadStore                 # 会话线程、分支、归档、上下文摘要
├── TurnEngine                  # 一次用户请求对应的可中断执行回合
├── AgentRuntime                # Agent 角色、子 Agent、工具权限、模型/预算
├── TaskScheduler               # 即时、后台、定时、批量任务统一队列
├── ResearchGraph               # 问题、假设、主张、证据、决策、运行、provenance
├── ArtifactReview              # 产物、版本、diff、评论、接受/拒绝、恢复、导出
├── QualityGates                # 引用、证据覆盖、复现性、文档、增量合并门禁
├── ResourceGovernance          # 并发、限流、成本、模型路由、失败策略
└── WorkspaceUI                 # 项目总览、线程、任务、证据矩阵、产物审阅、设置
```

### 1.1 统一对象关系

```text
Project
 ├── Thread
 │    └── Turn
 │         └── AgentItem / ToolItem / FileChangeItem / QualityItem
 ├── ResearchItem(question/hypothesis/objective/note)
 ├── Claim
 │    └── EvidenceLink → Evidence → Source/Artifact
 ├── ResearchRun → Task / Workflow / Artifact
 ├── Decision
 └── ProvenanceEdge
```

每个对象必须具备：稳定 ID、project_id、创建/更新时间、版本或状态、来源对象、可扩展
metadata，并能在前端互相跳转。

## 2. 分阶段执行计划

### Phase 0：基线冻结与迁移护栏（0.5–1 天）

目标：在重构前锁定现有行为和数据兼容性。

工作项：

1. 建立当前版本快照和协议清单。
2. 为 `PlatformStore`、`SourceStore`、`SessionStore`、`ArtifactStore` 添加迁移版本测试。
3. 编写旧数据 fixture：旧项目、旧任务、旧会话、旧论文目录、旧资料库。
4. 增加 `PROJECT_OS_VERSION` 和 feature flags，允许按项目逐步启用新工作台。
5. 为每个阶段定义“完成条件”和回滚路径。

验收：

- 旧数据库可自动迁移且任务/论文/会话仍可打开。
- 现有 Python、Vitest、TypeScript、Ruff 全量通过。
- 新旧 UI 可通过 feature flag 切换。

预计文件：`runtime/platform_store.py`、`web/app.py`、`config.py`、`docs/protocol.md`、`tests/`。

### Phase 1：统一 Project Space 和首页工作台（1–2 天）

目标：从“页面导航”升级为“项目中心”。

后端：

- 扩展 project API：项目摘要、活跃线程、运行中任务、未覆盖主张、最近产物、最近决策、
  最近质量风险。
- 增加统一搜索 API：线程、任务、资料、研究对象、产物、变更统一检索。
- 增加项目级事件流：任务状态、Agent 状态、质量告警、产物完成统一进入活动时间线。

前端：

- 新增 `ProjectHomeView`，作为默认首页。
- 左侧导航改为项目级结构，显示任务数量、风险数量、未读活动。
- 首页提供快速动作：新建研究任务、导入资料、添加问题、启动分析、打开最近产物。
- 当前会话、任务、证据和产物使用统一的 detail drawer，而非频繁离开当前页面。

验收：

- 用户打开项目后 5 秒内能看到“现在正在做什么、哪里有风险、下一步做什么”。
- 首页所有卡片均可跳转到真实对象详情。

预计文件：`frontend/src/App.tsx`、新建 `ProjectHomeView.tsx`、`lib/api.ts`、`web/routes.py`。

### Phase 2：Thread / Turn / Item 统一 Agent 交互协议（2–3 天）

目标：将现有 chat、task、workflow 统一到同一套 Agent 事件模型。

后端：

- 新增 `threads`、`turns`、`agent_items` 或兼容映射表。
- 将现有会话和 durable task 映射为 thread/turn。
- Item 类型至少包括：`user_message`、`agent_message`、`reasoning_summary`、`tool_call`、
  `tool_result`、`file_change`、`research_claim`、`evidence_link`、`quality_gate`、`approval`、
  `error`、`status`。
- 支持 `thread/start`、`thread/resume`、`thread/fork`、`turn/start`、`turn/steer`、
  `turn/stop` 的内部协议，并在现有 WebSocket 上保持兼容。
- 事件必须持久化、可回放、可分页、可按 after cursor 增量读取。

前端：

- 会话页和任务页共享 `ThreadTimeline` / `TurnTimeline` 组件。
- 工具调用、文件变更、证据、质量门禁均作为可展开 Item 卡片展示。
- 支持从任意完成的 Thread 分支出新线程；分支要带来源线程和上下文摘要。
- 支持在运行中直接 steer，不重置原回合。

验收：

- 断线后能恢复同一线程、同一回合的事件顺序。
- 用户可以从一个研究任务分支出“保守结论版”和“探索版”两个线程。
- 旧 `/ws/chat` 和 `/ws/generate` 测试保持通过。

预计文件：`runtime/platform_store.py`、`web/chat.py`、`web/ws.py`、`runtime/task_hub.py`、
`frontend/src/stores/`、`frontend/src/components/agent/`。

### Phase 3：Agent Supervisor 与真正多 Agent 协作（2–4 天）

目标：从静态 DAG 升级为可观测、可干预、可单独重跑的 Agent 协作系统。

后端：

- 新增 `AgentRun`、`AgentMessage`、`AgentArtifact`、`AgentBudget`、`AgentLease`。
- Supervisor 负责拆解、派发、合并和审阅；允许并发子 Agent。
- 每个角色独立配置：模型、reasoning effort、工具白名单、输入上下文、预算、超时、重试。
- 支持角色：Planner、Literature、Evidence、Data、Figure、Critic、Citation、Document、
  Synthesis。
- 支持节点级人工审批、节点级重跑、节点级跳过和人工接管。
- 每个 Agent 输出必须写入 provenance：输入 source、研究对象、脚本、数据 hash、产物。

前端：

- 新增 Agent 协作面板，显示每个 Agent 的状态、耗时、预算、工具调用和输出。
- 支持“只重跑 Literature Agent”“只重跑 Citation Gate”等精准动作。
- 支持点击 Agent 输出直接进入证据矩阵或产物审阅。

验收：

- 一个论文任务至少能并行运行 Literature / Data / Figure 三类 Agent。
- 任意子 Agent 失败不会丢失其他 Agent 产物。
- 用户可在合并前查看每个 Agent 的证据和结论。

### Phase 4：科研证据链和质量闭环（2–3 天）

目标：让“主张是否可信”成为系统的核心状态，而不是任务结束后的附加报告。

后端：

- 完善 evidence anchor：source_id、文件、页码、chunk、hash、excerpt、提取方式。
- 新增 claim coverage 规则：支持、反驳、待验证、来源冲突、过期证据。
- 将 Citation Gate、Doc Gate、数据复现检查统一写入 `quality_items`。
- 对每个结论生成质量报告和风险等级。
- 质量门禁支持增量执行：只审计发生变化的 claim/source/artifact。
- 引用审计结果持久化，支持 DOI、标题、作者、年份、BibTeX 差异说明。

前端：

- 新增“证据矩阵”视图：行=主张，列=证据，单元格=支持/反驳/缺失/冲突。
- 新增“来源链”时间线：问题 → Agent → 资料 → 分析运行 → 产物 → 决策。
- 风险面板优先显示未覆盖主张、冲突证据、失败运行和过期引用。

验收：

- 任何论文段落中的核心结论都能跳到至少一个证据锚点。
- 删除或修改来源后，相关主张自动标记为需要复审。
- 未通过 Citation Gate / Doc Gate 时，产物不能标记为 final。

### Phase 5：实验与分析可复现运行（2–3 天）

目标：让科研系统不仅“写论文”，还能够记录和复现分析。

后端：

- 新增 `AnalysisRun` / `ExperimentRun` 语义层，关联输入文件 hash、脚本 hash、参数、环境、
  Python 版本、模型、随机种子、输出 artifact。
- 提供运行 manifest 和一键重跑接口。
- 支持 CSV/JSON/Parquet/Excel 的数据摘要和 schema 变更检测。
- 记录 stdout、stderr、依赖、退出码和资源耗时。
- 失败运行自动进入质量风险面板。

前端：

- 新增数据分析运行列表和详情页。
- 支持输入、脚本、参数和输出的并排查看。
- 支持“复现运行”“比较两次运行”“将结果加入主张证据”。

验收：

- 同一输入 hash + 脚本 hash + 参数能够复现同一运行记录。
- 运行结果可以直接挂接到 claim/evidence/provenance。
- 运行失败可定位到具体命令、参数或输入文件。

### Phase 6：产物审阅中心（2–3 天）

目标：把产物审阅提升为核心交互，而不是文件树的附属功能。

后端：

- 新增 Artifact Review API：版本、审阅状态、评论、接受、拒绝、恢复、导出。
- 产物与 thread、turn、agent、task、run、claim、evidence 建立双向关联。
- 支持文档、表格、图片、PDF、代码、数据文件统一 artifact metadata。
- 对论文支持章节级、表格级、图级审阅记录。

前端：

- 新增 `ArtifactReviewView` / 右侧 Inspector。
- 文件预览、diff、来源、质量报告、评论在同一详情面板中切换。
- 提供“接受此版本”“恢复上一版”“要求 Agent 修改”“导出研究包”。
- 论文产物显示 citation/doc gate 状态和未解决风险。

验收：

- 用户无需离开当前线程即可审阅并接受 Agent 产物。
- 审阅动作可以回写任务状态和下一轮 Agent 输入。
- 导出包包含产物、来源、运行 manifest、引用审计和质量报告。

### Phase 7：统一调度、资源治理和通知（1–2 天）

目标：解决“执行感觉慢”和多任务资源不可控问题。

后端：

- 即时任务、后台任务、定时任务统一进入 Scheduler。
- 增加项目/Provider/模型/角色级并发限制。
- 增加 token、成本、耗时聚合：project/task/workflow/agent/role。
- 增加队列优先级、预估耗时、预算预警、超时策略和指数退避。
- 共享 HTTP client / connection pool，减少每轮连接建立成本。
- 对资料检索、prompt 组装和重复工具调用增加缓存。
- 增加任务完成、失败、需要审批、质量风险通知。

前端：

- 新增统一运行队列面板。
- 显示当前排队、执行、等待模型、等待工具、等待审批、失败重试状态。
- 显示预计等待时间和项目资源消耗。
- 支持暂停/恢复队列和调整优先级。

验收：

- 多任务并行时不会无限争抢模型或本地执行资源。
- 用户能解释“慢在哪里”：排队、模型首字节、工具、资料检索或质量门禁。
- 同一模型连接复用率和检索缓存命中率可观测。

### Phase 8：统一工作空间收敛与发布验收（2–3 天）

目标：将所有能力收敛为稳定、可持续使用的科研操作系统。

工作项：

1. 将首页改为 Project Home，旧页面保留为深链接和兼容入口。
2. 统一对象 ID、状态枚举、错误协议、分页、cursor 和权限检查。
3. 完善快捷键、命令面板、全局搜索、最近项目、固定项目和通知中心。
4. 增加项目导出/导入：排除 API Key 和内部临时文件，保留研究图谱和审计数据。
5. 增加完整 UI E2E：创建项目 → 提问 → 并行 Agent → 资料检索 → 分析运行 → 证据关联
   → 论文产物 → diff 审阅 → 接受/恢复 → 导出研究包。
6. 更新 README、PROJECT_STATUS、protocol、构建 hidden imports 和安装验证。

## 3. 推荐实施顺序

按用户价值和风险排序：

```text
Phase 0
  → Phase 1 Project Home
  → Phase 2 Thread/Turn/Item
  → Phase 4 Evidence & Quality
  → Phase 6 Artifact Review
  → Phase 3 Agent Supervisor
  → Phase 5 Reproducible Runs
  → Phase 7 Scheduler Governance
  → Phase 8 Release
```

原因：先统一交互对象和项目中心，再把科研质量与产物审阅嵌入主流程，最后扩展多 Agent
动态协作和资源治理。这样每个阶段都能独立交付，不会等到“大重构全部完成”才有可用结果。

## 4. 数据迁移策略

- `PlatformStore.SCHEMA_VERSION` 逐步递增，所有迁移幂等。
- 旧 `tasks` 映射到 `Thread/Turn` 的兼容视图，不立即删除旧表。
- 旧 `task_events` 映射为 `agent_items` 的只读历史。
- 旧 `run.json` / `events.jsonl` 继续作为文件协议兼容层。
- 旧论文目录自动生成 Artifact 和 ResearchRun 索引，不移动用户文件。
- 迁移前自动备份 `.ra/*.sqlite3`，失败时只回滚迁移副本。
- 所有导出包排除 `.env`、API Key、`.ra` 临时目录和系统缓存。

## 5. 性能与可靠性目标

| 指标 | 目标 |
|---|---:|
| 首页首屏本地渲染 | < 500 ms |
| 项目摘要 API | < 150 ms（无 LLM） |
| 线程恢复 | < 1 s 可见历史，后台继续回放 |
| 任务状态事件延迟 | p95 < 300 ms |
| 资料库重复检索 | 命中缓存后 < 100 ms |
| 任务断线恢复 | 事件不丢失，允许重复观察但不重复执行 |
| 单 Agent 崩溃 | 不影响其他 Agent 产物 |
| 质量门禁增量执行 | 只重算受影响对象 |
| 数据库迁移 | 幂等、可重复执行、失败不破坏旧数据 |

## 6. 安全与权限策略

- 项目级路径围栏继续保留。
- 读、写、执行、网络、外部连接器分别授权。
- Agent 角色拥有独立工具白名单。
- 人工审批必须绑定 tool call/item id，拒绝迟到或伪造响应。
- 后台/定时任务不得把明文 API Key 写入 payload、事件或产物。
- 产物导出必须过滤 `.env`、`.ra` 临时数据、缓存和密钥。
- 所有跨对象跳转都验证 project_id，禁止跨项目读取。

## 7. 测试和验收矩阵

### 后端

- 单元测试：对象 CRUD、版本、状态、provenance、质量门禁、队列租约、重试、触发器。
- 迁移测试：v3.4/v3.5 数据库 → 最新 schema。
- API 测试：分页、cursor、项目隔离、错误码、路径围栏。
- Agent 测试：steer、stop、resume、fork、审批、并发子 Agent。
- 复现测试：输入 hash + 脚本 hash + 参数 → 运行 manifest。

### 前端

- store reducer 测试：thread/turn/item 增量事件归约。
- 组件测试：项目总览、Agent 面板、证据矩阵、产物 Inspector、队列面板。
- 浏览器 E2E：断线、刷新、后台运行、分支、审阅、恢复、导出。
- 性能测试：1000 条事件、500 个证据片段、100 个任务并发浏览。

### 发布验收

```text
新建项目
 → 添加研究问题
 → 导入论文资料
 → 启动研究任务
 → 并行 Agent 执行
 → 生成主张和证据链接
 → 运行数据分析
 → 生成论文草稿
 → Citation/Doc Gate
 → 产物 diff 审阅

```

只有上述流程完整走通，才将项目标记为“科研操作系统 beta”。
